# pre-work 공개 뉴스레터 전환 설계

- 날짜: 2026-09-05
- 상태: 승인됨 (사용자)
- 범위: 사이트 전체 전환 — 콘텐츠 전면 재작성 + 카피 + 발행 파이프라인 + 페이지 구조 + 문서

## 목표

개인 학습 플랫폼으로 만들어진 pre-work를 외부 공개 뉴스레터로 전환한다.

- 정체성: **pre-work — 일 하기 전 10분, 개발자가 꾸준히 성장하기 위한 뉴스레터.** 이름은 유지한다.
- 독자: 실무 경력 0~10년 일반 개발자. 특정 회사·프로젝트 맥락은 제거한다.
- 콘텐츠: 기존 31호를 원본 소스로 삼아 **전면 재작성**한다(사용자 결정).
- 파이프라인: GitHub 이슈를 칼럼 요청 창구로 공개한다. 누구나 제출, 소유자가 `publish` 라벨을 달면 발행(승인 게이트 — 사용자 결정).
- 전환 전략: **B. 콘텐츠 완성 후 일괄 전환** — 31편 재작성을 먼저 끝내고 골격과 함께 스위치한다(사용자 결정).

## 비목표

- 시각 디자인 전면 개편 (design.md 체계 유지, 카피와 구조만 손댄다)
- 이메일 발송 시스템 신설 (RSS가 구독 수단. 발간 보고 메일은 운영자용으로 유지)
- 회원·구독 관리, 코멘트, 통계 도구
- 영문판

### /about/ 신설

- 이 뉴스레터가 무엇을 읽어주는지(10분 칼럼, takeaway, callout 구조)
- 어떻게 만들어지는지: GitHub 이슈로 칼럼 요청 → 소유자 승인(라벨) → 자정 발행
- 아카이브 성격 명시: "2026-09 아카이브 재편으로 이관된 글이다" (소급 날짜의 정직한 고지)

페이지·nav·footer 링크를 모두 지운다.

## 2. 칼럼 전면 재작성

### 번호·날짜

- **제1호부터 리셋.** 기존 31호는 git 히스토리에만 남고 사이트에서 제거된다.
- 기존 데이터의 호번호↔날짜 어긋남(미래 날짜 5개 포함)은 리셋으로 소멸한다.
- 새 날짜는 전환일에서 과거로 1일 간격 소급 배치한다(31편 ≈ 한 달치 아카이브).
  `/about/`에 이관 사실을 고지한다.

### 재작성 원칙

원본의 지식·구조·출처(`sources`)는 보존하고, 프레임만 바꾼다.

- "첫 출근", "우리 프로젝트", "회사에서" → 범용 상황 각색 ("레거시 Spring 프로젝트에 투입됐다면…")
- `callout`: "오늘 회사에서 해 볼 것" → **"오늘 해 볼 것"** — 독자 자기 실무에 적용하는 확인 가능한 행동
- 10분 안쪽, `takeaway` 한 문장, 평서형 종결, 과장 금지 — 기존 CONTENT.md 문체 규칙 유지
- 공개 원칙(CONTENT.md 상단) 강화 준수: 실제 소스·테이블명·접속정보 없음. 코드는 구조만 각색
- eGovFrame 소재는 공식 배포 표준이므로 유지하되 "내 회사" 프레임만 제거
- 호 간 `next` 참조는 새 번호 체계로 다시 잡는다 (기존 텍스트 참조 금지)

## 3. 발행 파이프라인 (핵심 기능화)

### 승인 게이트 (사용자 결정)

1. 누구나 `.github/ISSUE_TEMPLATE/` 양식으로 칼럼을 요청한다.
2. **자동 `publish` 라벨 부착을 제거한다** — 라벨은 저장소 쓰기 권한자만 달 수 있으므로
   소유자가 라벨을 다는 행위가 곧 승인이다. 미승인 이슈는 발행되지 않는다.
3. `publish` 라벨이 붙은 이슈는 기존 launchd 자동화(com.pre-work.publish-daily, 매일 00:05 KST)가
   읽어 칼럼으로 발행한다.
4. 발행된 칼럼 하단에 요청 이슈 링크를 크레딧으로 표기한다.
5. 발행 후 자동화가 해당 이슈에 발행 링크를 남기고 종결 처리한다.

### 변경 파일

- `.github/ISSUE_TEMPLATE/publish.yml`: 라벨 자동 부착 제거, 독자용 "칼럼 요청" 양식으로 재작성
  (주제, 알고 싶은 점, 배경 맥락)
- `.omp/publish-daily-issue.md`: 승인 게이트·이슈 크레딧·종결 절차 반영

  이슈 재작성에 맞춰 소개 문구 소폭 검수.
- **issues.ts**: 재작성 31편으로 교체. 기존 데이터는 git 히스토리로만 남는다.

## 6. 문서

- README.md: 공개 저장소 관점 전면 재작성 (제품 소개, 발행 구조, 개발 가이드)
- CONTENT.md: callout 정의, 칼럼 요청 파이프라인, 공개 원칙 재정리, /authoring 참조 제거

## 7. 검증·배포

1. worktree 브랜치에서 전체 작업, 완료 후 `main` 스쿼시 머지 + push (기존 컨벤션)
2. `npx astro build` — pagefind 인덱스 포함 빌드 성공
3. dev 서버에서 `/`, `/daily/1/`, `/about/`, `/drills/`, `/glossary/` 브라우저 확인
4. push 후 GitHub Actions "Deploy to GitHub Pages" 완료 확인
5. 승인 게이트 동작 확인: 라벨 없는 이슈가 발행 대상에서 제외되는지 템플릿·자동화 문서상 확인
